# OpenSpec: как мы ведём задачи

## Что это

OpenSpec — слой поверх Git. Перед написанием кода ИИ-ассистент и разработчик фиксируют в Markdown-файлах, **что** нужно сделать и **как понять, что готово**. План хранится в репозитории, его можно проревьюить, и он не теряется в истории чата.

OpenSpec не заменяет Git и не нужен для каждой задачи. Спецификации пишутся только для нетривиальных изменений.

## Структура

```text
openspec/
├── specs/              # Текущее поведение системы (источник правды)
├── changes/            # Одна папка = одно изменение
│   ├── <имя>/
│   │   ├── proposal.md # Зачем и что меняется
│   │   ├── specs/      # Delta-спеки (ADDED / MODIFIED / REMOVED) со сценариями WHEN / THEN
│   │   ├── design.md   # Технический дизайн (необязательно)
│   │   └── tasks.md    # Чеклист реализации
│   └── archive/        # Завершённые изменения
```

## Установка

```bash
npm install -g @fission-ai/openspec@latest
cd your-project
openspec init        # выбрать инструменты (Claude Code, Cursor, Copilot и др.)
openspec update      # обновить инструкции и команды для ИИ
```

Слэш-команды вводятся **в чате ИИ-ассистента**, а не в терминале.

## Пайплайн

```text
git switch -c <feature>
   │
/opsx:propose <feature>   # ИИ создаёт proposal, delta-спеки и tasks
   │
РЕВЬЮ ПЛАНА               # читаем файлы ДО кода, правим спеку, а не код
   │
/opsx:apply               # ИИ реализует по tasks.md
   │
/opsx:verify              # проверка соответствия спецификации
   │
git commit && open PR     # в PR попадают спеки и код
   │
Ревью PR → Merge
   │
/opsx:archive             # delta вливается в specs/, папка уходит в archive/
```

## Ревью PR

Порядок чтения, который стоит указать в описании PR:

1. `proposal.md` — правильно ли решаем проблему и не раздут ли скоуп.
2. Delta-спеки в `specs/` — корректно ли описано «готово» (сценарии WHEN / THEN).
3. `tasks.md` — адекватна ли декомпозиция.
4. Код — должен делать ровно то, что описано в спеке.

## Когда OpenSpec не нужен

- Мелкие правки, которые можно сделать за один коммит.
- Задачи, которые один разработчик держит в голове.
- Команда не будет читать файлы: тогда это лишь имитация процесса.
- Уже есть подробный тикет в Jira или Linear и он достаточен.

OpenSpec окупается, когда задача затрагивает несколько файлов или бизнес-логику, а ИИ регулярно делает не то, потому что требование не было зафиксировано.

## Важно

- Ассистенты работают лучше всего с моделями, сильными в рассуждениях, для планирования и реализации.
- Перед `/opsx:apply` очищайте контекст чата.
- Точный синтаксис команд зависит от инструмента. Смотрите подсказки, которые выводит `openspec init`.
