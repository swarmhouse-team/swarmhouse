# OpenSpec: пайплайн работы над задачами

## Цель

Изучить OpenSpec и описать, как мы ведём задачи с ним: от спецификации до PR.

Что выясняем:

- Что такое OpenSpec и как он устроен: спецификации, предложения изменений, задачи.
- Как он работает с нашими ИИ-инструментами (Claude Code и другими).
- Как встроить его в процесс: задача → спецификация → ревью → реализация → PR.
- Что хранится в репозитории и как это ревьюить.

Результат: пример задачи и пошаговый пайплайн её реализации с OpenSpec.

---

## 1. Что такое OpenSpec

OpenSpec — лёгкий слой поверх Git. Он заставляет разработчика и ИИ-ассистента договориться о том, что строим, **до** того как будет написана первая строка кода.

- Не заменяет Git и не требует описывать весь проект сразу.
- Спецификации пишутся только для нетривиальных изменений.
- План хранится в репозитории в виде Markdown-файлов, а не в истории чата. Его можно проревьюить, и он остаётся после мержа.

**Механика:** ИИ пишет план → человек утверждает его → ИИ реализует строго по плану.

### Структура папки `openspec/`

После `openspec init` в репозитории появляется папка `openspec/`:

```text
openspec/
├── specs/                  # Источник правды: как система ведёт себя СЕЙЧАС
│   └── <домен>/spec.md
├── changes/                # Одна папка = одно изменение
│   ├── <имя-изменения>/
│   │   ├── proposal.md     # Зачем нужно изменение и что меняется
│   │   ├── specs/          # Delta-спеки: ADDED / MODIFIED / REMOVED
│   │   ├── design.md       # Технический дизайн (необязательно)
│   │   └── tasks.md        # Чеклист реализации
│   └── archive/            # Завершённые изменения
└── config.yaml
```

| Сущность                  | Что это                                                                         |
| ------------------------- | ------------------------------------------------------------------------------- |
| `specs/`                  | Текущее поведение системы по доменам. Меняется только при архивировании.        |
| `changes/<имя>/`          | Изолированное предложение. Разные изменения не мешают друг другу.               |
| `proposal.md`             | Проблема, цель, скоуп.                                                          |
| `specs/` внутри изменения | Delta: что добавляется, меняется или удаляется. Сценарии в формате WHEN / THEN. |
| `tasks.md`                | Задачи, которые ИИ отмечает по ходу работы.                                     |
| `design.md`               | Технические решения, если они нужны.                                            |

Пример delta-спеки:

```markdown
## ADDED Requirements

### Requirement: Список чатов в боковой панели

Sidebar ДОЛЖЕН показывать список чатов пользователя, полученный через `GET /chats`.

#### Scenario: Успешная загрузка

- **WHEN** пользователь открыт в приложении и запрос `GET /chats` завершился успешно
- **THEN** в Sidebar отображается по одному элементу на каждый чат из ответа
```

Сценарий — проверяемое утверждение: ревьюер сразу видит, что считается «готово».

## 2. Работа с ИИ-инструментами

OpenSpec поддерживает десятки ассистентов, включая Claude Code, Cursor, GitHub Copilot, Gemini CLI и OpenCode. Для нас основной — Claude Code.

**Как это работает:**

1. В терминале запускаем `openspec init` и выбираем инструменты. OpenSpec создаёт для них слэш-команды или скиллы.
2. Слэш-команды вводим **в чате ассистента**, а не в терминале.
3. Ассистент читает `openspec/`, создаёт и обновляет артефакты, реализует задачи, сверяясь с файлами, а не с историей чата.

| Команда               | Что делает                                                                       |
| --------------------- | -------------------------------------------------------------------------------- |
| `/opsx:explore`       | Исследует проблему и код перед предложением                                      |
| `/opsx:propose <имя>` | Создаёт `proposal.md`, delta-спеки, `tasks.md` (и при необходимости `design.md`) |
| `/opsx:apply`         | Реализует задачи из `tasks.md`                                                   |
| `/opsx:verify`        | Проверяет, что реализация соответствует спецификации                             |
| `/opsx:archive`       | Вливает delta в `specs/` и переносит папку в `archive/`                          |

> Синтаксис команд зависит от инструмента. Например, для Claude Code это `/opsx:propose`, для других ассистентов он может отличаться. Точный вариант подсказывает `openspec init`.

**Разделение планировщика и исполнителя.** Технически возможно: один ассистент пишет план, другой выполняет. Передача идёт через файлы в `openspec/`. Но качество реализации зависит от исполнителя, и сильный план не спасёт слабую модель. Поэтому план и реализация ведутся одним инструментом, если нет явной причины делать иначе.

## 3. Встраивание в процесс

Пайплайн задачи:

```text
задача → спецификация → ревью плана → реализация → PR → ревью PR → merge → архивация
```

| Этап         | Команда / действие                                       | Кто                     |
| ------------ | -------------------------------------------------------- | ----------------------- |
| Ветка        | `git switch -c <feature>`                                | Разработчик             |
| Спецификация | `/opsx:propose <feature>`                                | Ассистент, по задаче    |
| Ревью плана  | Чтение `proposal.md` → delta → `tasks.md` до начала кода | Разработчик и ревьюер   |
| Реализация   | `/opsx:apply <feature>`                                  | Ассистент               |
| Проверка     | `/opsx:verify <feature>`                                 | Ассистент и разработчик |
| PR           | Коммит кода и папки `openspec/changes/<feature>/`        | Разработчик             |
| Ревью PR     | Спеки, затем код                                         | Ревьюер                 |
| Архивация    | `/opsx:archive <feature>` после мержа                    | Разработчик             |

Ключевое правило: **правки вносятся в спецификацию, а не в код**, пока план не согласован.

Когда OpenSpec нужен: задача затрагивает несколько файлов, бизнес-логику или интеграцию, и требование может быть понято по-разному.

Когда не нужен: мелкие правки, однофайловые исправления и задачи, полностью описанные в тикете.

## 4. Что хранится в репозитории и как это ревьюить

| Путь                                 | Что это                   | Как ревьюить                                        |
| ------------------------------------ | ------------------------- | --------------------------------------------------- |
| `openspec/specs/`                    | Текущее поведение системы | Читать как документацию                             |
| `openspec/changes/<имя>/proposal.md` | Цель и скоуп изменения    | Первым: правильная ли проблема и не раздут ли скоуп |
| `openspec/changes/<имя>/specs/`      | Delta-спеки со сценариями | Вторым: проверяемо ли определено «готово»           |
| `openspec/changes/<имя>/tasks.md`    | Чеклист реализации        | Третьим: адекватна ли декомпозиция                  |
| `openspec/changes/<имя>/design.md`   | Технические решения       | Если есть, смотреть архитектурные развилки          |
| Код в `src/`                         | Реализация                | Последним: должен делать ровно то, что в спеке      |

В описании PR стоит написать порядок чтения: «Сначала `proposal.md`, затем delta-спеку, затем код».

## 5. Пример задачи: пошаговый пайплайн

### Задача

Показывать в боковой панели (`Sidebar`) список чатов пользователя. Данные берём из эндпоинта `GET /chats`, описанного в `docs/api.md`.

Почему задача подходит для примера: она затрагивает API-слой, виджет `Sidebar` и состояние приложения, поэтому требования стоит зафиксировать до кода.

**Текущее состояние:** `src/widgets/Sidebar/ui/Sidebar.tsx` возвращает заглушку `<div>123</div>`. Папок `features/` и `entities/` в `src/` пока нет.

### Шаг 1. Подготовка (один раз)

```bash
npm install -g @fission-ai/openspec@latest
cd /f/TheLastTime/Chat
openspec init
```

При `openspec init` выбираем Claude Code. Слэш-команды появятся в чате Claude Code.

### Шаг 2. Ветка

```bash
git switch -c add-sidebar-chat-list
```

### Шаг 3. Предложение (`/opsx:propose`)

В чате Claude Code:

```text
/opsx:propose add-sidebar-chat-list
```

Ассистент создаёт `openspec/changes/add-sidebar-chat-list/` с файлами:

- `proposal.md`: проблема — Sidebar не показывает чаты; скоуп — только отображение списка, без создания и редактирования чатов.
- `specs/widgets/sidebar/spec.md`: delta-спека.

```markdown
## ADDED Requirements

### Requirement: Отображение списка чатов в Sidebar

Sidebar ДОЛЖЕН отображать чаты пользователя, полученные через `GET /chats`.

#### Scenario: Загрузка чатов

- **WHEN** Sidebar монтируется и `GET /chats` возвращает список
- **THEN** Sidebar показывает по одному элементу на каждый чат с его названием

#### Scenario: Пустой список

- **WHEN** `GET /chats` возвращает пустой массив
- **THEN** Sidebar показывает текст «Чатов пока нет»

#### Scenario: Ошибка запроса

- **WHEN** `GET /chats` завершился ошибкой
- **THEN** Sidebar показывает сообщение об ошибке и не падает
```

- `tasks.md`: чеклист.

```markdown
## 1. Данные

- [ ] 1.1 Добавить функцию запроса `GET /chats` через `shared/api`
- [ ] 1.2 Описать тип элемента чата

## 2. Интерфейс

- [ ] 2.1 Заменить заглушку в `Sidebar.tsx` на список чатов
- [ ] 2.2 Добавить состояния загрузки, пустого списка и ошибки

## 3. Проверка

- [ ] 3.1 Проверить отображение списка, пустого состояния и ошибки
```

### Шаг 4. Ревью плана (до кода)

Ревьюер проверяет по порядку:

1. `proposal.md`: проблема реальная, скоуп ограничен списком без создания чатов.
2. Сценарии: есть ли пустой список и ошибка. Если нет, дополняем спеку, а не код.
3. `tasks.md`: задачи достаточно мелкие и покрывают все сценарии.

Пока план не согласован, `/opsx:apply` не запускаем.

### Шаг 5. Реализация (`/opsx:apply`)

```text
/opsx:apply add-sidebar-chat-list
```

Ассистент идёт по `tasks.md`, пишет код и отмечает пункты. Если он отклонился от спеки, возвращаем его к `tasks.md`.

Перед этим полезно очистить контекст чата, чтобы ассистент опирался на файлы, а не на длинную историю.

### Шаг 6. Проверка (`/opsx:verify`)

```text
/opsx:verify add-sidebar-chat-list
```

Затем вручную:

```bash
npm run build
```

### Шаг 7. Коммит и PR

```bash
git add .
git commit -m "add sidebar chat list"
git push -u origin add-sidebar-chat-list
```

В описании PR:

> Порядок ревью: `openspec/changes/add-sidebar-chat-list/proposal.md` → delta-спека в `openspec/changes/add-sidebar-chat-list/specs/widgets/sidebar/spec.md` → `tasks.md` → код в `src/widgets/Sidebar/`.

### Шаг 8. Мерж и архивация

После мержа:

```text
/opsx:archive add-sidebar-chat-list
```

Delta вливается в `openspec/specs/widgets/sidebar/spec.md`, папка переносится в `openspec/changes/archive/`.

## 6. Итоговый пайплайн

```text
git switch -c add-sidebar-chat-list
   │
/opsx:propose add-sidebar-chat-list   ← proposal, delta-спека, tasks
   │
РЕВЬЮ ПЛАНА                           ← правим спеку, не код
   │
/opsx:apply add-sidebar-chat-list     ← реализация по tasks.md
   │
/opsx:verify add-sidebar-chat-list    ← соответствие спеке
   │
npm run build
   │
git commit && PR                      ← спеки + код
   │
Ревью PR: proposal → delta → код
   │
Merge
   │
/opsx:archive add-sidebar-chat-list  ← delta в specs/, папка в archive/
```
